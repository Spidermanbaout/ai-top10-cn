# Codex 使用入门：从打开项目到审查改动

> 面向第一次使用 Codex 的开发者。本文介绍如何选择使用方式、描述任务、检查代码改动，以及为项目保存长期有效的说明。界面和可用功能会继续更新；本文更新于 2026-10-09。

## Codex 能做什么

Codex 可以在你提供的项目上下文中阅读代码、解释结构、修改文件，并按你的要求运行本地开发工具。你负责确定目标和边界，Codex 负责探索和执行；最终仍由你检查改动并决定是否采用。

常见入口有三种：

- **ChatGPT 桌面应用**：适合打开本地项目、处理多文件任务，并在界面中查看执行过程和改动。
- **IDE 扩展**：适合边写代码边提问。打开文件和选中的代码可以作为上下文，改动也能在编辑器中查看。
- **命令行（CLI）**：适合在终端里工作、查看命令记录，或把 Codex 接入脚本和自动化流程。

刚开始时选自己最常用的入口即可，不需要同时配置全部入口。可从[官方快速入门](https://developers.openai.com/codex/quickstart)、[IDE 扩展指南](https://developers.openai.com/codex/ide)和[CLI 指南](https://developers.openai.com/codex/cli)查看当前安装步骤。

## 第一次打开项目

1. 在桌面应用中登录，选择 **Codex**，然后打开你希望 Codex 使用的项目文件夹。CLI 用户可以先在终端切换到仓库目录，再运行 `codex`。
2. 第一次先让它熟悉项目，不要直接要求大范围重写：

   ```text
   先阅读项目结构和 README，告诉我这个项目如何启动、主要模块在哪里、
   现有测试如何运行。先不要修改文件。
   ```

3. 如果项目很大，给出你关心的文件、功能或报错位置，能让它更快找到相关上下文。
4. 开始改动前，确认仓库状态。已有未提交工作时，先弄清哪些内容是你自己的，避免混淆。

## 把任务说清楚

好的任务描述让 Codex 知道要达到什么结果、应该参考什么信息，以及哪些边界不能越过。简单任务一句话就够；较大的任务可以包括目标、上下文、验收方式和限制。

**示例：修复一个可复现的问题**

```text
修复设置页打开“邮件通知”后刷新又恢复关闭的问题。

复现步骤：进入 /settings，打开邮件通知，点保存，然后刷新。
请先检查保存和读取设置的代码路径，再做最小范围修复。
保持现有 API 格式不变。完成后运行相关测试，并说明改了哪些文件、测试结果是什么。
```

**示例：先了解代码，再实施**

```text
先解释订单创建请求从路由到数据库的调用过程，列出涉及的文件和关键校验。
先不要修改。等我确认理解后，再根据这个方案增加重复请求保护。
```

你也可以明确写出“只分析，不修改”“运行测试前先告诉我命令”或“不要提交、推送、发布”。对于高影响操作，清楚写出边界；Codex 的权限和审批设置也可以控制它可执行的操作。

## 一个可靠的日常循环

### 1. 先读和规划

对于新模块或影响面较大的任务，先让 Codex 查找相关实现、调用方和测试，再请它列出方案与风险。你确认方向后，再开始编辑。

### 2. 分成可检查的小改动

把“重做整个系统”拆成具体结果，例如“在登录表单增加邮箱格式校验，并补充对应测试”。一次只交付一段范围明确的工作，方便发现偏差，也方便撤回。

### 3. 让它验证结果

告诉 Codex 项目通常使用的检查命令，并要求它报告实际运行了哪些命令。比如：

```text
完成后运行与本次改动相关的测试和 lint。
如果命令失败，请说明失败原因；不要把未运行的检查说成已通过。
```

### 4. 自己检查差异

查看改动的文件和关键代码，确认没有意外的配置、依赖或无关文件变更。可以在桌面应用或 IDE 中查看差异；CLI 可使用 `/review` 请求 Codex 检查本地改动。审查结果是辅助信息，提交前仍要确认行为符合预期。

### 5. 再决定提交

使用 Git 保存检查点，方便比较和回退。提交、推送或部署之前，确认改动范围、测试状态和目标分支；除非你明确要求，否则把这些发布动作留给你决定。

## 用 AGENTS.md 保存项目约定

如果每次都需要告诉 Codex 相同的项目规则，可以在仓库根目录添加 `AGENTS.md`。例如：

```markdown
# 项目说明

## 开发命令
- 安装依赖：npm ci
- 启动开发环境：npm run dev
- 运行测试：npm test

## 修改约定
- 尽量复用现有组件和样式。
- 改动 API 行为时补充或更新测试。
- 不要编辑生成目录 build/。
```

写清楚简短、稳定、可执行的约定即可。全局说明和仓库说明可以分层；需要更细的目录规则时，可以在对应子目录放置说明文件。官方文档介绍了 [AGENTS.md 的加载顺序和配置](https://developers.openai.com/codex/agent-configuration/agents-md)。

## 使用时的几个习惯

- **把密钥留在安全位置。** 不要把 API Key、密码、个人访问令牌或生产数据粘贴进提示词或提交到仓库。
- **先看再运行。** 安装依赖、数据库迁移、删除文件、部署等命令可能影响项目或外部环境；先理解命令做什么，再决定是否执行。
- **给足复现信息。** 报错文本、输入样例、复现步骤和期望行为，比“这里坏了，修一下”更容易得到可验证的修复。
- **遇到方向偏差就及时补充。** 说明哪个结果不符合预期、正确行为是什么，必要时要求它先撤回某段改动再继续。
- **把“完成”定义清楚。** 指定需要改哪些行为、需要通过哪些检查，以及哪些文件或行为必须保持不变。

## 可以直接复制的任务模板

```text
目标：
[希望完成的结果]

上下文：
[相关页面、文件、报错或复现步骤]

限制：
[不能改变的接口、目录、行为；是否允许新增依赖]

验收：
[要运行的检查，以及我如何判断结果正确]

请先检查项目并简要说明方案。完成后列出改动文件、运行过的命令及结果、仍需我确认的事项。
```
